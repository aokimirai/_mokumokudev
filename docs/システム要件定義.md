# システム要件定義書

## 1. やりたいこと

エンジニアのスキルを可視化し、プロジェクト情報を入力するだけでローカルLLMが保存済みの情報を分析し、アサインを提案してくれるシステムを作りたい。

## 2. 目的

- AIを使用して開発していくうえで、**人間が判断すべき部分はどのようなものか**を記録として残したい。
- そのために、会社でも使えそうなミニマムなシステムを生成AIを使用して開発する。

## 3. 仕様

### 3.1 ユーザー・権限管理

- ロールは最低2種類:「一般(エンジニア)」「マネージャー」

| ロール | 権限 |
| --- | --- |
| 一般(エンジニア) | 自分のスキル情報の閲覧・入力のみ |
| マネージャー | 全員のスキル閲覧、プロジェクト登録、AI提案の閲覧・最終アサイン決定 |

### 3.2 エンジニア・スキル管理

- エンジニア基本情報(氏名、役割、参画時期)
- スキルマスタ(カテゴリ:言語 / フレームワーク / DB / インフラ / ドメイン知識)
- スキルレベル・経験年数・最終使用時期の登録

### 3.3 プロジェクト管理(構造化フォーム入力)

- プロジェクト基本情報(名称、期間、ドメイン)
- 必要スキル × 必要レベル × 優先度を複数登録
- 登録済みプロジェクトの一覧・編集

### 3.4 AIアサイン提案

1. プロジェクトの必要スキルとエンジニアのスキルをDB側で事前フィルタ
2. 候補者のプロファイルをローカルLLMに渡し、適性スコアと理由文を生成
3. 提案結果の一覧表示(スコア順)

### 3.5 履歴・ログ管理

- 過去のアサイン実績(誰が・いつ・どの役割で・評価はどうだったか)
- AI提案のログ(何を提案し、実際に採用されたか)
  - → 精度検証や改善に使える

---

## 4. 本の構造

開発工程に沿って章立てをし、各章の末尾に「人間の判断」と「AIに任せた部分」を同じフォーマットで並べる**判断ボックス**を毎回挿入する構成とする。

読者(未経験〜駆け出しPG)にとって、判断基準が章ごとにパターン化されている方が、学びとして持ち帰りやすくなる。

### 4.1 章立て案(開発工程ベース)

1. 企画・要件定義:何を作るか、誰の課題を解くか
2. データ構造・DB設計(今回検討した部分)
3. 権限・ワークフロー設計(自己申告制にした経緯など)
4. LLM連携設計(プロンプト、事前フィルタの仕組み)
5. ローカルLLMにおぼれてみる
6. 実装
7. テスト・振り返り

### 4.2 各章共通の「判断ボックス」フォーマット

| 項目 | 内容 |
| --- | --- |
| 状況 | この工程で何を決める必要があったか |
| 人間が判断したこと | 誰が・どんな基準で決めたか |
| AIに任せたこと | 何を生成 / 提案させたか |
| 切り分けの基準 | なぜそこで線を引いたか |
| 振り返り | うまくいった点・修正した点 |

### 4.3 切り分け基準の軸(本の芯になる部分)

読者に伝わりやすい基準の例:

| 判断の種類 | 例 | 担当 |
| --- | --- | --- |
| 不確実性が高い判断 | 要件の解釈、権限設計の方針 | 人間 |
| 影響範囲が大きい / 後戻りしにくい判断 | データ構造、セキュリティ | 人間が最終決定、AIはたたき台 |
| 定型的・反復可能な作業 | コード生成、選択肢の洗い出し | AIに任せる |
